# 第11回 `src/qr.ts`：QR コード生成

このファイルは、**文字列を QR コードの白黒の点の並びに変換し、SVG の画像にする**部品です。外部のライブラリを使わず、QR コードの規格（JIS X 0510 / ISO/IEC 18004）に沿って自分で作っています（要件 7章）。

読み取りは、スマホの標準のカメラアプリに任せます（要件 3.3）。そのため、ここで作る QR コードは、どの機種のカメラでも読める正しいものでなければなりません。

他のファイルとは独立していて、数学的な内容が多い回です。全体の流れをつかんでから、細部を読むことをおすすめします。

---

## 1. 前提知識

### 1-1. QR コードの構造

QR コードの1つ1つの点を**モジュール**と呼びます。direct-share の接続用URL（60文字）は、33×33 モジュールの QR コードになります。

```
┌───────┐ │ ┌───────┐
│ ■■■■■ │ │ │ ■■■■■ │   ① 位置検出パターン（3つの角の大きな四角）
│ ■   ■ │ │ │ ■   ■ │       QR コードの位置と向きを見つけるための目印
│ ■ ■ ■ │ ② │ ■ ■ ■ │   ② タイミングパターン（白黒交互の線）
│ ■   ■ │ │ │ ■   ■ │       1モジュールの大きさを測るための目盛り
│ ■■■■■ │ │ │ ■■■■■ │   ③ 位置合わせパターン（小さな四角）
└───────┘ │ └───────┘       QR コードがゆがんでいても読めるようにする
─── ② ────┼──────────    ④ 形式情報（位置検出パターンの横）
          │      ③          誤り訂正のレベルと、マスクの種類
┌───────┐ │              ⑤ 型番情報（バージョン7以上のみ）
│ ■■■■■ │ │  データ      ⑥ データと誤り訂正の符号（残りすべて）
│ ...     │
```

①〜⑤を**機能パターン**と呼び、データ以外の決まった模様です。⑥がデータの領域です。

### 1-2. バージョン

QR コードの大きさは**バージョン**で決まります。バージョン1が 21×21 モジュールで、1つ上がるごとに縦横4モジュールずつ大きくなり、最大のバージョン40は 177×177 モジュールです。

```
1辺のモジュール数 = バージョン × 4 + 17
```

入れるデータが多いほど、大きなバージョンが必要です。

| 入れるもの | 長さ | バージョン |
|---|---|---|
| 接続用URL（ブローカー設定なし） | 60バイト | 4（33×33） |
| 接続用URL（ブローカー3件を含む） | 185バイト | 10（57×57） |

要件 6.1 で「ブローカー設定はデフォルトから変更されている場合のみURLに含める」としているのは、この差のためです（要件 R-11）。バージョンが大きいほど点が細かくなり、カメラで読み取りにくくなります。

### 1-3. 誤り訂正

QR コードは、一部が汚れたり欠けたりしても読めます。データに加えて**誤り訂正の符号**を入れておき、壊れた部分を計算で復元するためです。この符号には**リード・ソロモン符号**を使います。

誤り訂正の強さは4段階あり、このファイルは**レベル M**（約15% の破損を復元できる）に固定しています（要件 7章「誤り訂正レベルは1種類に固定」）。

| レベル | 復元できる量 | 特徴 |
|---|---|---|
| L | 約7% | データを多く入れられる |
| **M** | **約15%** | 一般的によく使われる |
| Q | 約25% | |
| H | 約30% | 汚れに強いが、同じデータでもバージョンが大きくなる |

### 1-4. リード・ソロモン符号の考え方

詳しい数学は専門書に譲り、ここでは考え方だけを説明します。

**データを「多項式」とみなし、決まった多項式で割った余りを誤り訂正の符号にします。**

普通の数の割り算でたとえます。データが `1234` で、`7` で割った余りは `2` です。`1234` と `2` を一緒に送れば、受け取った側は「`7` で割ると `2` 余るはず」と確かめられ、合わなければ壊れていると分かります。リード・ソロモン符号は、この考え方を多項式に広げたもので、どこが壊れたかを突き止めて、元に戻すこともできます。

ただし、普通の数の足し算や掛け算では、計算の結果がどんどん大きくなってしまいます。そこで、0〜255 の256個の数だけで閉じた、特別な足し算と掛け算を使います。これを **GF(2⁸)**（ガロア体）と呼びます。

| 演算 | GF(2⁸) での計算 |
|---|---|
| 足し算・引き算 | ビットごとの XOR（`^`）。足し算と引き算は同じ |
| 掛け算 | 特別な手順（`gfMul()`）。結果は必ず 0〜255 に収まる |

### 1-5. マスク

データの点の並び方によっては、白や黒が広い範囲で続いたり、位置検出パターンに似た模様ができたりして、カメラが読み間違えやすくなります。

そこで、決まった規則で一部の点の白黒を反転させます（**マスク**）。規則は8種類あり、それぞれで「読み取りにくさの点数」を計算して、いちばん点数の低い（読み取りやすい）ものを選びます。どのマスクを使ったかは、形式情報に書いておきます。

### 1-6. このファイルで出てくる書き方

| 書き方 | 意味 |
|---|---|
| `boolean[][]` | 真偽値の配列の配列（2次元の表）。`modules[y][x]` で、y 行目・x 列目の点（`true` が黒） |
| `Array.from({ length: n }, () => …)` | 長さ n の配列を作り、各要素を関数の戻り値にする |
| `new Array(n).fill(false)` | 長さ n の、すべて `false` の配列 |
| `^` | XOR（排他的論理和）。ビットごとに、違えば 1、同じなら 0 |
| `document.createElementNS(ns, 'svg')` | SVG の要素を作る。SVG は HTML とは別の「名前空間」の要素なので、`createElement` ではなくこちらを使う |

## 2. ファイルの全体像

`encodeQr()` の処理の流れ：

```
文字列
 │ ① UTF-8 のバイト列にする
 │ ② 入る大きさのバージョンを選ぶ
 │ ③ データのビット列を作る（モード、文字数、データ、終端、埋め草）
 │ ④ 8ビットずつのコード語にする
 │ ⑤ ブロックに分け、誤り訂正の符号を付け、交互に並べる
 │ ⑥ 機能パターンを描く
 │ ⑦ データを右下からジグザグに置く
 │ ⑧ 8種類のマスクを試し、いちばん良いものを選ぶ
 ▼
モジュール配列（boolean[][]） ──qrToSvg()──→ SVG の画像
```

| 名前 | 役割 |
|---|---|
| `ECC_PER_BLOCK`、`NUM_BLOCKS` | バージョンごとの、誤り訂正の符号の長さとブロックの数（規格の表） |
| `numRawDataModules()` | データに使えるモジュールの数 |
| `numDataCodewords()` | データに使えるコード語（バイト）の数 |
| `gfMul()` | GF(2⁸) の掛け算 |
| `rsDivisor()` | 割る多項式（生成多項式）を作る |
| `rsRemainder()` | 割り算の余り（誤り訂正の符号）を計算する |
| `alignmentPositions()` | 位置合わせパターンの位置 |
| `bit()` | 数の i ビット目を取り出す |
| `encodeQr()` | 本体（上の①〜⑧） |
| `penalty()` | 読み取りにくさの点数 |
| `qrToSvg()` | モジュール配列を SVG の画像にする |

使っているのは `main.ts` の1か所だけです：`$('qr').replaceChildren(qrToSvg(encodeQr(hostUrl)))`。

**このファイルの計算方法は、公開されている QR コード生成の解説（Project Nayuki の "QR Code generator library" など）で広く使われている手順に沿っています。** 規格の表や手順を正しく写しているかは、開発時に別の QR 読み取りライブラリ（jsQR）で、バージョン1〜38の QR コードを読み取って確かめました。

| 行 | 説明 |
|---|---|
| 4〜7 | バージョンごとの、1ブロックあたりの誤り訂正のコード語（バイト）の数。配列の位置がバージョン。バージョン0はないので、先頭は `-1`（使わない） |

これらの数は計算では出せない、規格で決められた値です。

**ブロック**：大きなバージョンでは、データをいくつかのブロックに分け、ブロックごとに誤り訂正の符号を付けます。リード・ソロモン符号は、1ブロックが長すぎると計算できなくなるためです。

### 14〜26行目：容量の計算

```ts
function numRawDataModules(ver: number): number {
  let result = (16 * ver + 128) * ver + 64;
  if (ver >= 2) {
    const numAlign = Math.floor(ver / 7) + 2;
    result -= (25 * numAlign - 10) * numAlign - 55;
    if (ver >= 7) result -= 36;
  }
  return result;
}
```

QR コード全体のモジュールから、機能パターンの分を引いた、**データ（と誤り訂正の符号）に使えるモジュールの数**を計算します。

| 行 | 説明 |
|---|---|
| 15 | バージョンに応じた全体の大きさから、位置検出パターン・タイミングパターン・形式情報の分を引いた数（を整理した式） |
| 16〜18 | バージョン2以上には位置合わせパターンがあるので、その分を引く。`numAlign` は1辺に並ぶ位置合わせパターンの数 |
| 19 | バージョン7以上には型番情報（18×2 = 36モジュール）があるので、その分を引く |

バージョン4では 807 モジュールです。

```ts
function numDataCodewords(ver: number): number {
  return Math.floor(numRawDataModules(ver) / 8) - ECC_PER_BLOCK[ver] * NUM_BLOCKS[ver];
}
```

**データに使えるコード語（バイト）の数**です。使えるモジュールを8で割ってバイト数にし（余りのビットは使わない）、誤り訂正の符号の分を引きます。

| バージョン | 全体（バイト） | 誤り訂正 | データ | 入る URL の長さ |
|---|---|---|---|---|
| 1 | 26 | 10 | 16 | 14バイトまで |
| 2 | 44 | 16 | 28 | 26バイトまで |
| 3 | 70 | 26 | 44 | 42バイトまで |
| **4** | **100** | **36**（18×2ブロック） | **64** | **62バイトまで** |
| 5 | 134 | 48 | 86 | 84バイトまで |

接続用URL（60バイト）は、バージョン4にぎりぎり収まります。

### 28〜36行目：`gfMul()`（GF(2⁸) の掛け算）

```ts
// GF(2^8) 上の乗算（原始多項式 0x11D）
function gfMul(x: number, y: number): number {
  let z = 0;
  for (let i = 7; i >= 0; i--) {
    z = (z << 1) ^ ((z >>> 7) * 0x11d);
    z ^= ((y >>> i) & 1) * x;
  }
  return z & 0xff;
}
```

GF(2⁸) での `x × y` を計算します。普通の掛け算の「筆算」を、ビットで行う形です。

| 行 | 説明 |
|---|---|
| 31 | `y` のビットを、上の桁（7ビット目）から順に見る |
| 32 | 今までの結果を左に1ビットずらす（2倍する）。8ビットからはみ出したら、`0x11D` と XOR して 0〜255 に戻す。`(z >>> 7) * 0x11d` は、はみ出したら `0x11D`、はみ出さなければ `0` |
| 33 | `y` のそのビットが 1 なら、`x` を足す（XOR する） |
| 35 | 下位8ビットを返す |

普通の掛け算の筆算と比べると、次の2点が違います。

- 足し算の代わりに XOR を使う（繰り上がりがない）
- 8ビットを超えたら、`0x11D` で「割った余り」に戻す

`0x11D`（2進数で `1 0001 1101`）は QR コードの規格で決められた数（原始多項式 x⁸ + x⁴ + x³ + x² + 1）で、この数で余りをとると、掛け算と割り算がきちんと成り立つ256個の数の世界になります。

### 38〜62行目：リード・ソロモン符号

```ts
function rsDivisor(degree: number): number[] {
  const result: number[] = new Array(degree).fill(0);
  result[degree - 1] = 1;
  let root = 1;
  for (let i = 0; i < degree; i++) {
    for (let j = 0; j < degree; j++) {
      result[j] = gfMul(result[j], root);
      if (j + 1 < degree) result[j] ^= result[j + 1];
    }
    root = gfMul(root, 0x02);
  }
  return result;
}
```

割る多項式（**生成多項式**）を作ります。`degree` は誤り訂正の符号の長さ（バージョン4なら18）です。

生成多項式は、(x − 1)(x − 2)(x − 4)(x − 8)… と、`degree` 個の式を掛け合わせたものです（1, 2, 4, 8… は GF(2⁸) で2を掛け続けた数）。

| 行 | 説明 |
|---|---|
| 39〜40 | 係数の配列を「1」（多項式の 1）で始める。一番大きい次数の係数（常に1）は省いて持っている |
| 41 | 次に掛ける (x − root) の root。最初は 1 |
| 42〜48 | (x − root) を `degree` 回掛ける。43〜46行目が「多項式に (x − root) を掛ける」計算で、各係数を root 倍し、隣の係数を足している |
| 47 | 次の root は2倍（GF(2⁸) で） |

この関数の結果は、バージョンごとに同じなので、1つの QR コードを作るときに1回だけ呼びます。

```ts
function rsRemainder(data: number[], divisor: number[]): number[] {
  const result: number[] = new Array(divisor.length).fill(0);
  for (const b of data) {
    const factor = b ^ (result.shift() as number);
    result.push(0);
    divisor.forEach((coef, i) => {
      result[i] ^= gfMul(coef, factor);
    });
  }
  return result;
}
```

データの多項式を生成多項式で割った**余り**を計算します。これが誤り訂正の符号になります。普通の数の筆算の割り算と同じ流れで、1桁（1バイト）ずつ処理します。

| 行 | 説明 |
|---|---|
| 53 | 余り（途中経過）。生成多項式の長さ分の0で始める |
| 54 | データを1バイトずつ見る |
| 55 | 今の先頭の桁を取り出し、次のデータのバイトと足す。これが「この桁で何倍を引くか」になる。`result.shift()` は先頭を取り出して配列を1つ縮める。`as number` は、配列が空でないので `undefined` にならない、と TypeScript に伝えている |
| 56 | 末尾に0を足して、長さを戻す（1桁ずらしたことになる） |
| 57〜59 | 生成多項式の `factor` 倍を引く（GF(2⁸) では XOR） |
| 61 | 残ったものが余り |

### 64〜75行目：位置合わせパターンの位置と、ビットの取り出し

```ts
function alignmentPositions(ver: number): number[] {
  if (ver === 1) return [];
  const numAlign = Math.floor(ver / 7) + 2;
  const step = ver === 32 ? 26 : Math.ceil((ver * 4 + 4) / (numAlign * 2 - 2)) * 2;
  const result = [6];
  for (let pos = ver * 4 + 17 - 7; result.length < numAlign; pos -= step) result.splice(1, 0, pos);
  return result;
}
```

位置合わせパターンの中心の座標（縦横共通）の一覧を返します。

| 行 | 説明 |
|---|---|
| 65 | バージョン1にはない |
| 66 | 1辺に並ぶ数。バージョン2〜6は2つ、7〜13は3つ…と、7バージョンごとに1つ増える |
| 67 | 間隔。規格の表を再現する式。バージョン32だけは式に合わないので、例外として26にしている |
| 68〜69 | 最初は 6（タイミングパターンの位置）。最後は右端から7の位置で、そこから間隔ずつ戻りながら、2番目の位置に差し込んでいく（`splice(1, 0, pos)` は、位置1に `pos` を挿入する） |

バージョン4では `[6, 26]` です。縦横の組み合わせは (6,6)、(6,26)、(26,6)、(26,26) の4つですが、3つは位置検出パターンと重なるので、実際に描くのは (26,26) の1つだけです（156行目）。

```ts
function bit(x: number, i: number): boolean {
  return ((x >>> i) & 1) !== 0;
}
```

数 `x` の、下から `i` 番目のビットが 1 なら `true` を返します。

### 78〜86行目：バージョンを選ぶ

```ts
/** テキストをQRコードのモジュール配列（true = 黒）に変換する */
export function encodeQr(text: string): boolean[][] {
  const data = new TextEncoder().encode(text);

  let ver = 1;
  for (; ver <= 40; ver++) {
    const ccBits = ver <= 9 ? 8 : 16;
    if (4 + ccBits + data.length * 8 <= numDataCodewords(ver) * 8) break;
  }
  if (ver > 40) throw new Error('QRコードに収まらない長さです');
```

| 行 | 説明 |
|---|---|
| 79 | 文字列を UTF-8 のバイト列にする。QR コードの「バイトモード」で入れるため |
| 81〜85 | バージョン1から順に、入るかどうか調べる。必要なビット数は、モード（4ビット）＋文字数（バージョン9までは8ビット、10以上は16ビット）＋データ |
| 86 | バージョン40でも入らなければ、例外を投げる（約2,300バイト以上） |

QR コードには、数字だけを効率よく入れる「数字モード」などもありますが、URL は英字や記号を含むので、何でも入る「バイトモード」だけを使っています。

### 88〜104行目：データのビット列

```ts
  // データのビット列
  const bits: number[] = [];
  const push = (val: number, len: number) => {
    for (let i = len - 1; i >= 0; i--) bits.push((val >>> i) & 1);
  };
```

ビット（0 か 1）を1つずつ並べる配列と、数 `val` を `len` ビットで（上の桁から）並べる関数です。

```ts
  push(0b0100, 4);
  push(data.length, ver <= 9 ? 8 : 16);
  for (const b of data) push(b, 8);
```

| 行 | 書くもの | 例（60バイトの URL） |
|---|---|---|
| 93 | モード：`0100` はバイトモード | `0100` |
| 94 | データのバイト数 | `00111100`（60） |
| 95 | データ本体 | `01101000`（`h`）`01110100`（`t`）… |

```ts
  const capacity = numDataCodewords(ver) * 8;
  push(0, Math.min(4, capacity - bits.length));
  push(0, (8 - (bits.length % 8)) % 8);
  for (let pad = 0xec; bits.length < capacity; pad ^= 0xec ^ 0x11) push(pad, 8);
```

| 行 | 説明 |
|---|---|
| 96 | データに使える全ビット数（バージョン4なら 64 × 8 = 512） |
| 97 | **終端**：「データはここまで」を表す0を最大4ビット書く |
| 98 | 8ビットの区切りに合うよう、0で埋める |
| 99 | **埋め草**：残りを `0xEC` と `0x11` を交互に書いて埋める（規格で決まった値）。`pad ^= 0xec ^ 0x11` は、`pad` が `0xEC` なら `0x11` に、`0x11` なら `0xEC` に切り替える書き方 |

60バイトの URL では、4 + 8 + 480 = 492ビットに、終端の4ビットで496ビット（ちょうど8の倍数）、残り16ビットを `0xEC 0x11` で埋めて512ビットになります。

```ts
  const codewords: number[] = [];
  for (let i = 0; i < bits.length; i += 8) {
    codewords.push(bits.slice(i, i + 8).reduce((a, b) => (a << 1) | b, 0));
  }
```

## 5. 理解チェック

1. 接続用URL（60バイト）は、なぜバージョン4になるのですか。
2. ブローカーの設定を変えていないときは、URL にブローカーを含めないのはなぜですか。
3. GF(2⁸) で、足し算に XOR を使うのはなぜですか。
4. データを複数のブロックに分けて、交互に並べる（インターリーブ）のはなぜですか。
5. 形式情報を2か所に書くのはなぜですか。
6. マスクを試した後に、同じマスクをもう一度かけているのはなぜですか。
7. どのマスクを選んでも正しく読める QR コードになるのに、点数で選んでいるのはなぜですか。
8. QR コードの周りに4モジュールの白い余白を付けるのはなぜですか。

<details>
<summary>答え</summary>

1. バイトモードでは、モード4ビット＋文字数8ビット＋データ480ビット＝492ビットが必要で、レベル M のデータ容量はバージョン3が352ビット（44バイト）、バージョン4が512ビット（64バイト）だから。入る最小のバージョンが4。
2. ブローカーの URL を含めると185バイトになり、バージョン10（57×57）の大きな QR コードになる。点が細かくなって、カメラで読み取りにくくなるため（要件 6.1、R-11）。
3. GF(2⁸) では、繰り上がりのない足し算を使うことで、結果が必ず 0〜255 に収まるため。ビットごとに繰り上がりなしで足すと、ちょうど XOR になる。
4. QR コードの一部分がまとめて汚れたときに、その破損を複数のブロックに分散させるため。1つのブロックに破損が集中すると、そのブロックの復元できる量を超えてしまう。
5. 形式情報（誤り訂正のレベルとマスクの番号）が読めないと、QR コード全体が読めなくなるため。1か所が汚れても、もう1か所から読めるようにしている。
6. マスクは白黒の反転なので、同じマスクを2回かけると元に戻る。次のマスクを試す前に、元の状態に戻すため。
7. マスクによって、同じ色が長く続いたり、位置検出パターンに似た模様ができたりして、カメラが読み間違えやすくなることがあるため。点数の低い（読み取りやすい）マスクを選ぶ。
8. 周りの模様（ページの背景など）と QR コードの境目を、カメラがはっきり区別できるようにするため（規格の決まり）。

</details>
